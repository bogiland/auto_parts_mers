# NAA.md — передача проекта в T3

Состояние на 13–14 ноября 2026 года. Это описание локальной рабочей копии, а не обещание, что всё перечисленное уже опубликовано. Сначала изучить этот файл, затем `AGENTS.md` в корне проекта и в `web/`, `docs/product-context.md` в корне и фактический код. Старый `README.md` описывает ранний HTML-макет Mercedes и не является актуальной спецификацией.

## 1. Что за продукт

NAA.md — сайт каталога и приёма заказов автозапчастей для разборки в Слободзее (ПМР). Основа ассортимента — бывшие в употреблении детали примерно со 150 автомобилей-доноров; многие автомобили поступают в сборе, включая двигатели и КПП. Есть новые расходники. Целевая аудитория — ПМР и Молдова. Каталог в будущем должен охватывать разные марки; текущие демонстрационные товары преимущественно Mercedes-Benz и не должны превращаться в постоянное ограничение бизнеса.

Цены: основная валюта MDL, вторичная — рубли ПМР. Курс `rubPerMdl` вводит владелец в настройках; сейчас он `null`, поэтому вторую валюту нельзя показывать как рассчитанную. Интерфейс предполагает RU/RO, но полноценная румынская локализация пока не реализована.

Оплата только при получении либо переводом после подтверждения оператором, без онлайн-оплаты. Самовывоз: Слободзея, ул. Новосовицкая 25, точка 9:00–18:00. До 20 км доставка по договорённости; дальше маршруткой либо службой доставки за плату. Стоимость и наличие подтверждает оператор с 8:00 до 20:00. Двигатели и КПП возврату не подлежат. Не добавлять поиск по VIN и госномеру. Состояние и донор конкретной детали отложены до задачи 9: не выдумывать эти данные.

Настроенные локально контакты: ПМР `+373 777 45 636`, Молдова `+373 68 270 269`; Viber и Telegram ориентированы на номер ПМР. Телефоны, адрес и часы лежат в строке `settings` базы SQLite, а не в виде захардкоженных рабочих контактов в коде. В `config/checkout-settings.json` телефоны пустые как значения по умолчанию; при работе локального сайта используются сохранённые значения БД. Ссылки на конкретный Viber/Telegram-профиль в настройках пусты, код строит переход по телефону. Реальное открытие обоих мессенджеров на устройствах клиентов надо отдельно проверить.

## 2. Где проект и как запускать

- Локальная папка: `D:\NAA\auto_parts_mers-main\web`.
- Стек: Next.js 16.3.5 (App Router), React 19.2.8, TypeScript, Tailwind CSS 4, PostgreSQL 17 (`pg`), Playwright для проверок.
- В PowerShell: `cd D:\NAA\auto_parts_mers-main\web`, затем `npm run dev`. Открыть `http://localhost:3000` и `http://localhost:3000/admin/login`.
- Зависимости в этой локальной папке установлены (`node_modules` есть). В новом окружении потребуется `npm install`.
- Проверки: `npm run lint`, `npx tsc --noEmit`, `node qa/aggregate-checkout-smoke.mjs`, `node qa/admin-shell-smoke.mjs`. Общее `npm run qa` и другие smoke-сценарии есть в `qa/`.
- Репозиторий git есть, origin — github.com/bogiland/auto_parts_mers. Перед заменой папки делать резервную копию кода и дамп базы (`npm run db:up` + `pg_dump`).
- Сейчас в БД нет активного Owner и Operator. Для входа создать владельца командой `npm run staff:create-owner` внутри `web`; сценарий интерактивно спросит имя, телефон и пароль. Не использовать номера тестовых сотрудников из QA как рабочие учётные записи.
- Production-сборка `npm run build` в этой среде завершалась `EPERM` при создании внутренних папок `.next`, в том числе при попытке использовать отдельный каталог сборки. ESLint, TypeScript, локальные страницы и ключевые smoke-проверки проходили. Причина `EPERM` не устранена: не заявлять, что production-сборка проверена.

## 3. Реализованные клиентские экраны

| Адрес | Состояние |
| --- | --- |
| `/` | Главная: шапка с поиском и навигацией, баннеры, «Товар недели», подбор с помощью эксперта, категории, товары, бренды, промоблоки и футер. Данные товаров в основном демонстрационные из `src/data/homepage.seed.ts`. |
| `/catalog`, `/catalog/[direction]`, вложенные категории | Каталог и разделы, карточки, фильтры и адаптивные варианты. `/catalog` переводит в `/catalog/legkovye`. Не считать весь ассортимент реальным складом. |
| `/search`, `/api/search/suggest` | Поиск и подсказки по текущим данным каталога. |
| `/products/[id]` | Страница товара из текущих данных. |
| `/cart` | Корзина без входа в `localStorage`: добавление/количество, ограничение остатком, удаление и возврат в течение 5 секунд, пустое состояние, загрузка и ошибка, мобильный итог над нижним меню, `noindex`. Проданный товар не включается в итог. Данные состояния и донора не придумывать. |
| `/checkout` | Три блока: контакт, способ получения, оплата; телефон, способ связи, адрес при доставке, согласия. Вторая обязательная галочка возникает для товара с `return_restricted`. Заказ сохраняется в SQLite, сервер проверяет остаток и цену, считает итог, использует idempotency key против дублей. После отправки показывается квитанция. |
| `/favorites` | Избранное без входа в `localStorage`, с пустым состоянием и отметкой проданного, `noindex`. |
| `/order/s/[token]` | Личная ссылка на статус по случайному UUID, `noindex`; неверный код даёт 404. Публичная страница не показывает телефон, имя и адрес. |

Заказы действительно пишутся в `orders` и `order_items` базы, а не только в браузер. Данные цены/остатка берутся из `catalog_products`, текущие карточки главной связаны с ними через `src/lib/live-catalog.ts`. Новая деталь, заведённая в админке, попадает в таблицу и checkout API, однако **не появляется автоматически в визуальной сетке публичного каталога**, которая строится из seed. Это отдельная интеграционная задача.

## 4. Админка и роли

Адреса `/admin/login`, `/admin/dashboard`, `/admin/[section]`. Файлы: `src/app/admin/[section]/page.tsx`, `src/components/admin/AdminShell.tsx`, `admin-sections.ts`, `RecordList.tsx`, `PhotoUploader.tsx`, `src/app/admin/admin.css`; серверная логика в `src/lib/staff-db.ts`, `staff-auth.ts`, API в `src/app/api/staff/`.

- Вход сотрудника: телефон и пароль, единый текст ошибки, ограничение попыток, `HttpOnly` cookie. Сессия отзывается при выходе, бездействие два часа её завершает. Есть серверный выход со всех устройств, но в новом каркасе админки видна только обычная кнопка выхода; отдельное действие «выйти на всех» следует вернуть в интерфейс.
- Owner имеет доступ к финансам, отчётам, себестоимости, экспорту, пользователям, настройкам и журналу. Operator видит операционные разделы. Прямой переход оператора в owner-разделы закрыт. Телефон клиента в списке маскирован, раскрытие по кнопке пишет запись в журнал.
- Тёмный фон и панель в палитре шапки/футера NAA, белый текст, красный акцент. Слева группа навигации шириной 240 px; активный пункт со светлой подложкой и красной чертой. Сверху поиск по номеру заказа/телефону/ID/seed SKU, `Ctrl+K` и `/`, переключение светлой и тёмной темы, колокольчик со счётчиком новых заказов/обращений. На телефоне боковая панель выезжает, внизу быстрое меню и красный `+`.
- Заказы, обращения, заявки, детали и себестоимость выводятся списком с поиском/статусом/сортировкой/страницей в URL. Клик открывает карточку справа, на узком экране она занимает ширину экрана. Можно менять статусы заказов и обращений, цену и остаток, импортировать CSV, добавлять обращение и деталь. В карточке детали есть загрузка до 8 фото: выбор файла/камера, уменьшение в браузере, перетаскивание порядка; сервер сохраняет файлы в `public/uploads/`, список путей — в SQLite. Нужна дальнейшая проверка на реальных мобильных устройствах и связь этих фото с публичной карточкой.
- В настройках Owner можно изменить оба телефона, адрес, часы, курс и при необходимости ссылки на мессенджеры. Курс оставлен пустым для владельца. В журнале есть события входа, изменения статусов, цены/остатка, импорта, роли, удаления пользователя, просмотра телефона и фото/добавления детали.

**Не путать каркас с полной CRM.** Не сделаны отдельные рабочие модули возвратов, задач, доноров, справочников, баннеров, витрины, вакансий/откликов, страниц сайта и безопасности. Они скрыты, а не ведут в пустую страницу. `Клиенты` сейчас основаны на списке заказов, самостоятельной карточки клиента и полноценной истории нет. `Деньги` и `Отчёты` показывают простую сводку из заказов, без законченной аналитики, учёта расходов и периода; надпись «Всё время» не является интерактивным фильтром. Колокольчик показывает счётчик, полноценного центра уведомлений нет. Быстрое действие `+ Заказ` ведёт на публичный `/checkout`, отдельной формы заказа оператора нет. Не во всех разделах оформлены законченные состояния загрузки/ошибки и единая таблица дизайна. Светлая тема есть, но основной запрос владельца — тёмная фирменная CRM.

## 6. Визуальные и продуктовые пробелы, важные для T3

1. Сравнить текущие экраны со снимками владельца и `qa/shots/`: админка пока выглядит как аккуратный тёмный каркас, а не законченная CRM уровня примера b-prod. Нужны более проработанные дашборд, таблицы, чипы, фильтры, панель объекта, пустые/загрузочные/ошибочные состояния, подтверждения и тосты. Референса `docs/reference/admin-examples/` в локальной папке не было; доступны изображения из переписки пользователя.
2. Привести дизайн админки к проектным правилам `AGENTS.md`. Сейчас `admin.css` содержит отдельные значения размеров и цветов, местами отличается от общих токенов `globals.css` и строгой типографики/отступов. Перед массовой переработкой сделать визуальную проверку 360/390/768/1024/1280/1440.
3. Привязать новые детали и загруженные фото из админки к публичному каталогу и карточке. Сейчас seed ограничивает отображаемые товары; не заполнять донора и состояние фиктивными данными до задачи 9.
4. Завершить полноценные страницы/функции CRM по отдельным задачам, а не выводить их пустыми пунктами. Отдельно нужны нормальный поиск по всем реальным SKU/артикулам, создание заказа оператором, клиенты, задачи/возвраты/доноры и справочники, маркетинг, расширенные финансы/отчёты и уведомления.
5. После ввода курса владельцем проверить вторую валюту на карточке, корзине, оформлении и статусе заказа. Проверить реальные Viber/Telegram-ссылки и возможность подготовить текст «Заказ №...». Сейчас телефонная ссылка может зависеть от настроек приватности и установленного приложения.
6. Устранить `EPERM` при `npm run build`, затем провести production-проверку. Dev-режим Next иногда показывал временный 500 при первом компилировании отдельного маршрута после горячих правок; повторное открытие помогало. Это не равно проверенной стабильности production.
7. Не переносить слепо старый README или старую формулировку «только Mercedes» / VIN. Опираться на бизнес-контекст владельца и текущий код.

## 7. Очередность продолжения

Сначала сделать резервную копию локальной папки и SQLite; создать Owner через интерактивный скрипт; ввести курс в `/admin/settings`. Затем решить проблему production-сборки и проверить браузерные сценарии. После этого заняться связыванием админского склада/фото с витриной, визуальной полировкой CRM и следующими предметными модулями. Не отправлять изменения на GitHub без отдельной просьбы владельца: он просил прежде всего видеть изменения локально на порту 3000.
